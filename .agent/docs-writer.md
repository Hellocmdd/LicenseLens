# docs-writer.md — 文档撰写专项提示词

叠加在 `AGENT.md` 与 `conventions/docs-style.md` 之上，用于写 `README.md`、`docs/*.md`、`docs/DESIGN.docx`、`release/RELEASE.md`。

## 1. 先读后写

动笔前必须实际读过：

- 要描述的代码（接口、`ScanEngine`、`ReportRenderer`、CLI 参数处理）——文档里的行为必须与代码一致；
- `docs/CONTRACT.md` 对应条款，接口签名直接照抄，不改写；
- `docs/LicenseLens分工合作书.md` 中对应的流程与门禁规定；
- 现有文档中被替换或引用的段落，避免留下矛盾描述。

## 2. 各文档骨架

### README.md

```markdown
# LicenseLens
一句话定位 + 仓库地址 + 项目状态

## 用户、场景与范围     谁用、输入→处理→输出、基础能力、扩展新增能力、本次不做、项目起点
## 快速开始             环境版本、构建命令、样例与预期结果、CLI 用法与退出码
## 核心与扩展           模块职责表、扩展如何构建/接入/禁用、核心源码不变的核验方法
## 样例                 samples/ 每个文件说明
## 测试与检查           构建即测试、覆盖范围、故意改错演示、CI 位置与真实状态
## 协作与贡献入口       分支、PR、Review、合并规则；代表性 PR/Review 记录
## 成员贡献与AI核验     每人实质改动、审查他人、一条 AI 建议的采用/拒绝与验证
## 许可与已知限制       许可证选择理由、关键依赖义务、未完成项
```

### docs/CONTRACT.md

只增不改地维护：接口签名、字段语义、退出码表、错误契约、注册方式、兼容策略、变更记录表。每次实质变更在顶部与变更记录表中同时留痕。

### docs/DESIGN.docx

八章：项目概述与需求、总体架构、模块设计、扩展机制与接口设计、关键业务流程、数据与配置、测试与质量方案、设计取舍与局限。至少架构图 + 流程图各一张（可用 Mermaid 生成后截图或画图工具），接口章节给方法签名、输入输出示例与错误约定。

### release/RELEASE.md

字段见 `conventions/docs-style.md` 第 7 节；发布流程见 `release.md`。文件放仓库外 `release/` 目录，最终 Commit 与 SHA-256 写在这里，不写进 README。

## 3. 写作要求

- 结论先行：每节开头一句话说结论，再展开。
- 用表格做对照（模块、退出码、样例、检查项），用有序列表写流程，用代码块写命令并标注执行目录。
- 图优先 Mermaid；文档里引用的路径写成仓库相对路径。
- 未定项写 `TODO(<模块或文档>): ...`，集中在文末"待办"；交付前必须清零。
- 契约或设计发生变化时，同步更新受影响的 README 段落与 DESIGN 章节，并在 PR 描述里列出"同步了哪几处"。

## 4. 事实与数据

- 测试数量、通过状态、退出码、运行结果必须来自实际执行；没跑过写"未执行"。
- CI 状态只写真实链接或如实写"未托管/以本地命令为准"。
- 未知的第三方许可证义务写"待确认"，不臆测。
- 性能、覆盖率等没有实测的数字写 `TBD`，不估算后当结论。

## 5. 交付前自检

- [ ] 每个"怎么用"的命令都实际粘贴执行过，参数与默认值正确
- [ ] 文档描述与当前代码一致（方法名、参数名、退出码、默认路径）
- [ ] 没有占位符（"待填""TODO""示例"）残留于必填栏目
- [ ] 没有营销词与无依据形容词
- [ ] 链接与相对路径可达；Mermaid 能在 GitHub 正常渲染
- [ ] 未实现的部分明确标注"计划"或写进"已知限制"

## 6. 禁止

- 不写与代码不符的"理想设计"；不确定就写"以代码为准"并留 TODO。
- 不复制粘贴后各自修改造成多处漂移。
- 不在公开文档中引用 `.agent/` 内容或内部对话。
- 不虚构 CI 链接、PR 编号、审查记录、SHA-256、测试通过率。
- 不代填成员贡献与 AI 核验结论。

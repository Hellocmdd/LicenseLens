# docs-style.md — 文档规范

适用：`README.md`、`docs/` 下全部 Markdown、`docs/DESIGN.docx`、`release/RELEASE.md`、`samples/` 下的样例说明。具体文档的章节骨架由 `../docs-writer.md` 提供，本文档管通用写作与格式规则。

## 1. 每份文档只回答一类问题

| 文件 | 回答什么 | 不写什么 |
| --- | --- | --- |
| `README.md` | 怎么装、怎么跑、怎么测、怎么接入扩展、怎么贡献 | 架构推导、内部设计取舍 |
| `docs/CONTRACT.md` | 接口签名、退出码、错误契约、注册与兼容策略 | 实现步骤、教程 |
| `docs/LicenseLens分工合作书.md` | 模块归属、协作流程、Gate 与门禁 | 技术细节 |
| `docs/DESIGN.docx` | 系统怎么组织、为什么这样设计、接口与流程怎么工作 | 逐步操作教程 |
| `release/RELEASE.md` | 本次发布的身份、制品、摘要、实际运行结果 | 未来计划 |

- 同一内容只在一处写全，其他位置用相对路径链接引用，不复制粘贴后各自漂移。
- 发现两处描述冲突，先确认哪个与当前代码一致，再统一修改；不要两边都改一半。

## 2. 结构

1. **目的**：开头一两句说明读者是谁、这份文档回答什么问题。
2. **结论先行**：3–5 行摘要，把最重要的结论放在最前。
3. **主体**：分节，每节只回答一个问题；标题层级从 `#` 起，每份文档只有一个一级标题。
4. **待办**：未定项统一写 `TODO(<模块或文档>): <一句话>`，集中放在文末"待办"小节；括号里写模块或文档区域，不写人名。
5. **关联**：文末列"相关文档"，写相对路径。

- 优先用表格做对照（字段、退出码、检查项），用有序列表写流程，用代码块写命令。
- 图优先用 Mermaid（`flowchart TD`、`sequenceDiagram`），不贴截图；必须贴图时放 `docs/images/` 并用相对路径引用。
- 代码块必须标语言（`java`、`bash`、`powershell`、`text`、`mermaid`）。

## 3. 语言与事实

- 中文撰写；术语首次出现附英文，全文保持一致译法。
- 命令必须可复制执行：写全参数、注明执行目录、区分 Windows PowerShell 与 bash 差异。
- 路径用反引号包住，写成仓库相对路径；不出现本地绝对路径（`D:\...`、`C:\Users\...`）。
- 数字、结论必须有实际来源：测试通过数、退出码、耗时来自真实运行；没跑过就写"未执行"或 `TBD`。
- 禁止"业界领先""高性能""大幅提升""完美解决"这类无依据形容词；禁止猜测性描述（"应该可以""一般都能"）。
- 外部链接写全 URL；GitHub Actions 运行编号、PR 编号必须真实存在，编不出就如实写"未托管/未执行"。

## 4. 格式约定

- 中英文之间加空格，数字与单位之间不加空格；不混用全角与半角标点。
- 列表项以句号结尾或不结尾，同一份文档内保持一致；列表嵌套不超过两层。
- 表格对齐用 Markdown 标准写法，列宽不必对齐源码。
- 不使用 HTML 布局；不用多个连续空行制造间距。
- 文件末尾保留一个换行。

## 5. README 必备栏目

按交付要求，README 需包含：用户、场景与范围（含"本次不做"）；快速开始（环境、构建、样例、预期结果，命令标注执行目录）；核心与扩展（如何构建、接入、禁用、重启要求，"核心源码不变"的核验方法）；测试与检查（构建/测试命令、三类行为分别验证什么、故意改错演示、CI 位置与真实状态）；协作与贡献入口（分支、PR、Review、合并规则）；成员贡献与 AI 核验表；许可与已知限制。

- 不保留模板占位符（"待填""TODO""以下是示例"）。
- "已知限制"要写实：哪些功能是骨架、哪些测试未写、哪些文档未完成。

## 6. DESIGN.docx 要求

- 章节：项目概述与需求、总体架构、模块设计、扩展机制与接口设计、关键业务流程、数据与配置、测试与质量方案、设计取舍与局限。可按实际合并，但核心设计内容不能缺。
- 至少一张总体架构图 + 一张关键流程图或时序图。
- 接口章节必须写关键方法、输入输出示例与错误约定，不能只列接口名。
- 模块章节标注对应代码目录，不逐类罗列。
- 未实现的标注"计划"，不能把计划写成已实现。
- 与提交版本一致：代码变了就更新；导出约 8 页或以上，不以页数评分。
- 排版：标题用 Word 内置样式，代码用等宽字体，图表加编号与标题（图 1、表 1）。

## 7. RELEASE.md 字段

版本及选择理由、最终 Commit 完整 SHA、Tag 及其目标 Commit、工作区状态与构建/测试结果、CI 真实状态、交付物名称与环境要求、运行命令、SHA-256、核心场景与扩展操作的实际结果、本次变化与已知限制、发布决定（RELEASE / HOLD 及理由）。

- 多个运行文件时，用"相对路径 + SHA-256"表格。
- 写 `HOLD` 时说明缺口，不隐瞒未验证项。

## 8. 修改文档的流程

- 纯文档改动单独提交，`docs(<scope>)`，scope 取 `readme`、`contract`、`design`、`plan`。
- 契约类文档（`CONTRACT.md`）的实质改动走契约变更流程，PR 标 `[CONTRACT-CHANGE]`。
- 文档改动与代码改动同时需要时，先改文档、再改代码，最后一起提交并互相链接。
- 改完自查：所有链接可达、所有命令可执行、所有数字与当前代码一致。

## 9. 禁止事项

- 禁止在公开文档中粘贴 `.agent/` 提示词内容或内部对话。
- 禁止写"AI 说没问题""AI 已验证"作为证据；验证结论只写实际执行的命令与结果。
- 禁止把占位符、示例数据、过期截图留在交付文档里。
- 禁止虚构 CI 链接、PR 编号、审查记录与 SHA-256。
- 禁止在文档里承诺范围外的功能（传递依赖、联网查询、GUI、Gradle 等）。

# commit-push-confirm.md — 提交、推送、合并、打标签前的确认协议

前置：本文档约束 AI 在开发期执行的所有 git 写操作。
核心原则：**AI 不得在开发者明确确认之前执行任何 git 写操作。**

## 1. 写操作（必须逐次确认）

- `git commit`（含 `--amend`）
- `git push`（含 `--force`、`--force-with-lease`、推送标签）
- `git merge`、`git rebase`、`git cherry-pick`
- `git reset`（除 `--soft` 以外）
- `git branch -d` / `-D`、删除远端分支
- `git tag`（创建或删除）
- `git stash drop` / `clear`
- 修改 `.gitignore`、`.gitattributes`
- 任何改写已推送历史的操作

## 2. 读操作（无需确认）

`git status`、`git log`、`git diff`、`git show`、`git branch`（仅列出）、`git tag`（仅列出）、`git remote -v`、`git stash list`。

## 3. 确认请求格式

执行写操作前先输出：

```text
[待确认] <操作类型>：<一句话说明>

变更范围：
- 涉及文件：<文件列表或数量>
- 提交信息：<完整 commit message，仅 commit 时填写>
- 影响面：<是否推送远端 / 是否改写历史 / 是否影响他人分支>

风险提示：
- <无则写"无"；有则逐条列出，如"将改写已推送的 main 历史，其他人需要重新拉取">

请确认是否执行。回复"确认"继续；"取消"终止；给出修改意见则调整后重新请求。
```

只有收到明确同意（"确认""可以""执行""OK"）后才能执行，模糊回复不算同意。

## 4. 分批规则

- 一次确认只覆盖一次操作。`commit` 与 `push` 必须分开确认，不得合并成一次请求。
- 同一会话内连续多次 `commit`，每次都重新确认，不沿用上一次的同意。
- 批量脚本（一次生成多个 commit）必须整体说明并逐条列出 commit message，确认后按列表执行，执行中不得临时增删。
- 提交前先给出 `git status` 的实际结果，确保只包含本次相关文件。

## 5. 例外与升级

- 开发者明确说"本轮提交不用问"时，只在当前这一轮有效，会话结束即失效；`push`、`merge`、`tag` 仍需单独确认。
- `--force`、`reset --hard`、删除远端分支、改历史**不存在自动执行例外**，每次单独确认。
- 涉及 `main` 的任何写操作，必须显式写出"目标是 main 分支"。
- 涉及发布（Tag、交付物、SHA-256）的操作，要同时说明是否会破坏已记录的历史与摘要一致性。

## 6. 执行前自检

- [ ] 已按第 3 节格式输出确认请求
- [ ] 开发者已明确同意
- [ ] 实际执行范围与确认请求一致，未临时扩大
- [ ] `push` 已确认远端与目标分支
- [ ] `--amend` / `--force` / 改历史已单独提示风险并获同意
- [ ] `git status` 中无构建产物、密钥、无关文件

## 7. 与其他规范的关系

`AGENT.md` 的禁区 N9 声明"不擅自执行 git 写操作"，本文档是它的落地细则；冲突时以更严格的一侧为准。
若开发者要求违反本文档，先说明风险，再按第 3 节正式请求确认。

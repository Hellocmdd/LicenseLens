# .agent — 开发期 AI 协作提示词

## 这个目录是什么

存放开发期调用 AI 助手时使用的系统提示词与规范，**随仓库提交、全组共享**，任何成员修改后其他成员直接拉取即可生效。

- 本目录**不属于项目产出**：不参与 `mvn` 构建，不进入 `release/` 交付物，不被任何 Java 代码引用，也不出现在 `docs/DESIGN.docx` 的设计描述里。
- 本目录**不要加入 `.gitignore`**。团队共享是前提，忽略它会让成员的 AI 行为不一致。
- 本目录只描述"如何协助开发"，不描述"业务怎么实现"；具体实现与契约写在仓库代码和 `docs/CONTRACT.md` 里。

## 文件索引

| 文件 | 用途 | 何时加载 |
| --- | --- | --- |
| `AGENT.md` | 主提示词：角色、项目速览、任务类型、硬约束、工作流、输出格式、自检 | 每次会话的基础，其他文件叠加其上 |
| `review.md` | 代码审查：审查顺序、输出格式、必跑命令 | 提交前自查、PR Review 前预审 |
| `test-writer.md` | 测试：T1–T9 矩阵、断言要求、故意改错演示 | 写测试、补测试、跑测试 |
| `docs-writer.md` | 文档：README / CONTRACT / DESIGN / RELEASE 的骨架与要求 | 写、改文档 |
| `release.md` | 发布：冻结、打 Tag、打包、摘要、交付自检 | 准备版本发布与交付 |
| `conventions/code-style.md` | Java 代码风格、集合与排序、异常、依赖边界、测试代码 | 写、改、审查代码 |
| `conventions/comment-style.md` | 注释与 Javadoc：写什么、必须写在哪、TODO 格式 | 写注释、补 Javadoc、清理 TODO |
| `conventions/docs-style.md` | 文档通用规范：职责分工、结构、语言与事实、格式 | 任何文档任务 |
| `conventions/git-workflow.md` | 分支、提交信息、PR 与 Review、契约变更、标签与发布 | 任何 git 写操作前 |
| `conventions/commit-push-confirm.md` | commit/push/merge/tag 的确认协议 | git 写操作前无条件必读 |

## 两类提示词

- **场景型**（根目录）：`review` / `test-writer` / `docs-writer` / `release`，对应具体任务，按需叠加。
- **规范型**（`conventions/`）：跨任务的通用约束，按主题拆分，独立维护。

`AGENT.md` 是底座，其余文件都与它叠加使用；规范型文件本身不重复 `AGENT.md` 中的角色与流程。

## 使用方式

1. 会话开始时把 `AGENT.md` 作为系统提示词。
2. 任务命中某个场景时，再叠加对应的场景文件。
3. 需要写代码、写注释、写文档、执行 git 写操作时，按 `AGENT.md` 第四节的索引加载规范文件，不要预读全部。
4. 只读 git 命令（`status`/`log`/`diff`）无需加载任何规范。

## 修改规则

1. **不写死分工**：不写成员姓名、学号、GitHub 用户名，也不写"A 负责 X / B 负责 Y"这类固定归属。角色由本次任务和仓库中的分工文档决定，提示词只描述任务类型与模块边界规则。
2. **不标注权威来源**：不在提示词里建"某文档最高权威"的排序；规范内容直接写成规则本身。发现提示词与代码或文档不一致时，要求 AI 报告差异而不是自行择一执行。
3. 新增**协作场景**：在根目录建独立 `.md`，并在本 README 登记。
4. 新增**通用规范**：在 `conventions/` 下建独立 `.md`，并在本 README 与 `conventions/README.md` 双重登记。
5. 修改后自检：是否与 `docs/CONTRACT.md` 的契约冲突？是否与 `AGENT.md` 的硬约束 N1–N12 冲突？是否出现了具体人名或固定分工？
6. 目录本身随仓库提交；更改后由修改者在 PR 描述里说明"改了哪条规则、为什么"。
